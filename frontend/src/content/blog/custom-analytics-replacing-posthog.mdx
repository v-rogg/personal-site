When I rewrote my personal site, I decided to ditch PostHog and build my own analytics. Not because PostHog is bad - it's actually excellent - but because sometimes the simple solution is the right one.

### Why Replace PostHog?

**Data Residency**: Even with PostHog EU, my data was still on third-party servers. For GDPR compliance, having everything on my own German VPS is much cleaner. No data processing agreements, no third-party sub-processors.

**Cost**: PostHog's free tier is generous, but scales can tip quickly. My custom solution costs exactly 0 EUR on top of my existing VPS.

**Integration**: I wanted tight integration between analytics and my signature feature. Who drew what, how long did they spend, what was their journey? With custom analytics, these joins are trivial.

**Overkill**: PostHog has feature flags, session replay, A/B testing, funnels, and dozens of other features. For a personal site, I need page views and custom events. That's it.

### What I Track

The tracking is intentionally minimal:

**Page Views**
- URL and referrer (external only - no internal navigation tracking)
- Scroll depth (how far down the page)
- Timestamp

**Custom Events**
- Signature editor: open, save, undo, redo, eraser toggle
- Carousel: navigation, autoplay state
- Blog: tag clicks, time on page
- Contact form: submissions

**Sessions**
- Anonymous session ID (generated client-side)
- Country and region (from GeoIP lookup)
- First seen / last seen timestamps

### The Implementation

The entire backend analytics is about 200 lines of Rust:

```rust
// Event ingestion endpoint
pub async fn track_event(
    State(state): State<Arc<AppState>>,
    Json(req): Json<TrackEventRequest>,
) -> Result<Json<()>, AppError> {
    let now = chrono::Utc::now().timestamp();
    
    sqlx::query(
        "INSERT INTO events (id, session_id, event, properties, ts) 
         VALUES (?, ?, ?, ?, ?)"
    )
    .bind(uuid::Uuid::new_v4().to_string())
    .bind(&req.session_id)
    .bind(&req.event)
    .bind(&req.properties)
    .bind(now)
    .execute(&state.db)
    .await?;

    Ok(Json(()))
}
```

The client-side is even simpler - about 50 lines of TypeScript that sends events to `/api/tracking/events` with the session ID and event data.

**No cookies**. The session ID is generated once with `crypto.randomUUID()` and stored in sessionStorage. Close the tab, get a new session. Simple.

### GDPR Compliance Benefits

This setup makes GDPR compliance trivial:

1. **All data stays on my German VPS** - no third-party transfers
2. **No third-party data sharing** - I'm both controller and processor
3. **Anonymous by design** - no PII stored, just session IDs
4. **Easy data deletion** - `DELETE FROM events WHERE session_id = ?`
5. **No consent required** - anonymous analytics don't need consent under GDPR

I don't track:
- IP addresses (only used for GeoIP lookup, not stored)
- User agents
- Device fingerprints
- Cross-site tracking
- Any personally identifiable information

### Merging Analytics with Signatures

The real power comes from joining analytics with signature data. Every signature has a `session_id`, so I can ask questions like:

**Drawing Duration**: How long between opening the editor and saving?

```sql
SELECT 
    s.id,
    s.name,
    (save_event.ts - open_event.ts) as duration_seconds
FROM signatures s
JOIN events open_event ON open_event.session_id = s.session_id 
    AND open_event.event = 'signature_editor_open'
JOIN events save_event ON save_event.session_id = s.session_id 
    AND save_event.event = 'signature_saved'
WHERE save_event.ts > open_event.ts
ORDER BY duration_seconds DESC
```

**Conversion Funnel**: What percentage of people who open the editor actually save?

```sql
SELECT 
    COUNT(DISTINCT CASE WHEN event = 'signature_editor_open' THEN session_id END) as opened,
    COUNT(DISTINCT CASE WHEN event = 'signature_saved' THEN session_id END) as saved
FROM events
```

**Engagement Metrics**: How many times did they use the eraser?

```sql
SELECT 
    s.id,
    COUNT(*) as eraser_toggles
FROM signatures s
JOIN events e ON e.session_id = s.session_id 
    AND e.event = 'signature_eraser_toggled'
WHERE e.ts BETWEEN s.ts_created - 3600 AND s.ts_created + 60
GROUP BY s.id
```

### Drawbacks and Trade-offs

Let's be honest about the downsides:

**Manual Implementation**: I had to build everything myself. PostHog gives you dashboards, funnels, retention charts out of the box. I have SQL queries.

**No Fancy Dashboards**: My "dashboard" is running queries in the SQLite CLI. For a personal site, this is fine. For a business, you'd want something more polished.

**No Real-Time**: I query data when I want to see it. There's no live dashboard showing current visitors. Again, fine for a personal site.

**Single Server Scale**: This approach doesn't scale horizontally. But for a personal site getting a few hundred visits a day, SQLite handles it effortlessly.

**Implementation Time**: Building this took a day. Setting up PostHog takes 10 minutes. The ROI only makes sense if you have specific requirements like mine.

### SQLite is Fine

I want to address the elephant in the room: "SQLite for analytics? Really?"

Yes. Here's why:

**Low Traffic**: My site gets maybe 100-500 page views per day. SQLite can handle thousands of writes per second.

**WAL Mode**: Write-Ahead Logging means reads never block writes. Multiple concurrent requests are no problem.

**Single-File Backup**: `cp app.db backup.db` - done. No database server to maintain, no connection pooling to configure.

**Query Performance**: With proper indexes, even queries over millions of rows complete in milliseconds.

The tech industry has overcomplicated data storage. For the vast majority of applications, SQLite is not just adequate - it's optimal.

### Results

After running this for a few weeks, here are some actual numbers from my site:

- **16.7% editor conversion rate** - people who open the editor and save a signature
- **Average drawing time: ~13 minutes** - people really take their time
- **Longest session: 30 minutes** - someone was very dedicated
- **5.3 average eraser uses per drawing** - mistakes happen

These insights would be buried in PostHog's interface. With custom analytics, they're a SQL query away.

### When to Use This Approach

Custom analytics makes sense when:

- You want full data ownership
- You have specific integration requirements
- You're comfortable with SQL
- Your traffic is moderate (sub-10k daily)
- You don't need real-time dashboards

Stick with PostHog/Plausible/etc when:

- You need a team to access dashboards
- You want plug-and-play setup
- You need advanced features (session replay, A/B testing)
- You're scaling to millions of events
- You don't want to maintain code

For my personal site, the custom approach is perfect. Full control, zero cost, and exactly the features I need.
